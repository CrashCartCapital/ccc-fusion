# CI fast-gate plan — Gate reuses Build's dist (2026-09-03)

Work package WP-A of a CI speed plan scoped to `.github/workflows/pr-checks.yml` only (a sibling work package, WP-B, is a read-only slot-count proposal package and touches nothing here). Branch `agent/ci-fast-gate-20260903`.

## Ground truth (measured, run 33738197262 on 9ed3acc02)

All five PR jobs (Lint, Typecheck, Build, Gate, Desktop packaging) run on the M2 Max inside the Colima `ci` VM. 12 runner containers share the VM; fusion runners are capped at 2.5 GiB / 2 CPU each (runner processes idle at ~640 MiB inside that cap), the bwrap runner at 4 GiB / 4 CPU. A host-level admission service holds every job in "Set up runner" until one of two global FIFO slots frees, shared across four repos — so "Set up runner = 8 min" was queue wait, not container boot.

Per-job slot time before this change:

| Job | Slot time | Notes |
|---|---|---|
| Lint | ~1.5 min | |
| Typecheck | ~4 min | builds core+engine itself |
| Build | ~8 min | `pnpm build`, 408 s; desktop vite build ran inside CLI full packaging and OOMed once at the 1664 MB heap cap |
| Gate | ~8 min | ~5 min of it was a redundant `pnpm build` — its dist-cache key missed on every PR whose sources differed from main, and its path list omitted `packages/cli/dist` anyway |
| Desktop packaging | ~6 min | separate advisory workflow, same slots |

Slot-minutes ≈ 27.5 over 2 slots → ~14 min floor; observed 15 min.

## What changed

1. **Build saves its full dist set; Gate restores it instead of rebuilding.** Build's "Build" step (`pnpm build`) already runs the identical build Gate used to repeat. Build now runs `actions/cache/save@v4` afterward under key `fusion-pr-dist-v1-${{ runner.os }}-${{ runner.arch }}-${{ github.sha }}` over the same 10 package/plugin dist paths `scripts/ensure-test-artifacts.mjs`'s `REQUIRED_BUILD_PACKAGES` needs, plus `.fusion/cache/plugin-build-cache.json` (this dist set is the same one `full-suite.yml`'s `fusion-dist-v2-` cache already publishes — mirrored mechanics, separate key prefix so the two workflows can never hand each other a partial path list). Gate gets `needs: build` and replaces its old `actions/cache@v4` step (an 8-path list that omitted `packages/cli/dist`, so a hit could never make boot-smoke's `packages/cli/bin.mjs` valid) with `actions/cache/restore@v4` on the identical key and path list. Exact-match key only, no `restore-keys` (stale dist is the known failure mode, FN-4232/FN-4605); never `node_modules`.
2. **Gate keeps `pnpm build` as a graceful fallback on a genuine miss, not a hard failure and not an unconditional no-op on a hit**: no `fail-on-cache-miss`, and the "Build" step is now `if: steps.dist-cache.outputs.cache-hit != 'true'`. See "Adjudicated corrections" below for why the first cut of this PR ran it unconditionally on the (wrong) assumption that it would be a fast skip.
3. **Lint and Typecheck stay independent** (no `needs`). They're short, and the shared host-level admission service already globally serializes runner slots across repos — an added `needs` edge there would only add latency, not save a redundant build.
4. **Desktop OOM: built as its own step, not a raised heap.** PR Checks run 33704433491 OOMed the Build job — `[desktop:build] vite build --base ./` hit "Ineffective mark-compacts near heap limit" inside `@runfusion/fusion build: build:tsup:serial`. Root cause: CI always runs the CLI's tsup build in "full package" mode (`wantsFullCliPackage()` treats `CI=true` as an implicit `--full`), and full-package mode stages the desktop Electron runtime by spawning `pnpm --filter @fusion/desktop build` as a **child of the still-live CLI tsup process** (`packages/cli/tsup.config.ts` `ensureDesktopRuntimeAssetsBuilt`, invoked from its `onSuccess` hook). Both processes inherit the job's `NODE_OPTIONS=--max-old-space-size=1664` and can be resident at once inside the runner's 2.5 GiB container cap, whose own processes already use ~640 MiB.

   `desktop-packaging.yml` runs the exact same command (`pnpm --filter @fusion/desktop build`) with the exact same 1664 MB cap, **alone**, and passes — proving the desktop build itself doesn't need more heap; it needs to not run concurrently with another live Node process holding a comparable heap in the same container. `packages/desktop/scripts/build.ts` (via `workspace-tools.ts`) is already self-contained — it builds `@fusion/core`, `@fusion/engine`, and the dashboard runtime itself, so it needs nothing pre-built. The fix: add a standalone "Build desktop runtime (staged ahead of CLI full packaging)" step — same command, same 1664 MB cap — **before** the `pnpm build` step. `ensureDesktopRuntimeAssetsBuilt()` short-circuits on `existsSync(packages/desktop/dist)` (verified: `packages/cli/tsup.config.ts` line ~346), so the nested spawn — and the two-process memory contention that caused the OOM — never happens. The job-wide heap is not raised above the already-proven-safe 1664 MB ceiling; it's relocated to a step where nothing else is competing for it. **This fix is scoped to the Build job only** — see "Known residual gap" below for Gate's own fallback build path.

## Adjudicated corrections (2026-09-03, after review of the first cut)

A review pass caught two design errors in the first version of this change before commit. Both are fixed in the workflow now; recorded here so the reasoning isn't lost.

1. **Cache key: commit-exact (`${{ github.sha }}`), not a source-content hash.** The first cut keyed the cache on `scripts/ensure-test-artifacts.mjs --print-source-hash`, which only hashes `REQUIRED_BUILD_PACKAGES`' own source directories. Two different commits that differ only in a path outside that hashed set (`packages/i18n`, an unbundled plugin, a root config file, etc.) would produce the *same* hash — so Gate could restore a save that actually belongs to a different commit than the one it's testing, a genuine stale-dist risk. Keying on `${{ github.sha }}` instead makes the save/restore pair commit-exact: Gate (`needs: build`) always runs in the same workflow run as Build, so restoring under the identical `github.sha` guarantees it's this exact commit's own output. A rerun of the same commit still hits; every other commit gets its own Build run first, so Gate can never be handed a stranger's save.
2. **Gate's `pnpm build` fallback must be conditional on a miss, not run unconditionally.** The first cut's reasoning — "on a hit, the restored dist plus `--seed-artifact-cache` make `pnpm build` a fast content-hash skip" — was wrong on inspection of two things:
   - `scripts/build-workspace.mjs` (what `pnpm build` actually runs) keeps its *own* skip-cache at `.fusion/cache/plugin-build-cache.json` (`BUILD_CACHE_FILE`), which is git-ignored and untouched by `--seed-artifact-cache` (that flag only seeds `ensure-test-artifacts.mjs`'s separate `artifact-cache.json`, and none of `test:gate`'s actual constituent `package.json` scripts call `ensureTestArtifacts()` anyway — grepped for it). On a fresh checkout `plugin-build-cache.json` doesn't exist, so `evaluatePackageBuild`'s cache lookup returns `"no-cache"` → `shouldBuild: true` for every package regardless of whether dist was just restored.
   - `wantsFullCliPackage()` treats `CI=true` as an implicit `--full` unconditionally, and `ensureFullPackageCliPlanned()` then force-plans `@runfusion/fusion` into the build even when its own cache entry says "unchanged" — so the CLI's full tsup packaging pass (the exact pass that risks the nested desktop OOM) would run again on *every* Gate invocation regardless of the dist restore.

   So an unconditional `pnpm build` on a hit would have silently redone the entire Build-job build inside Gate — none of the intended time savings, just extra work hidden behind a green check. Fixed two ways: the "Build" step is now `if: steps.dist-cache.outputs.cache-hit != 'true'` (today's full-build behavior, unchanged, on a genuine miss only), and `.fusion/cache/plugin-build-cache.json` now rides along in the cached path list, so a hit gives Gate the literal "already built this exact source" record Build itself just wrote — a real skip if anything downstream ever does invoke `build-workspace.mjs` again. A new unconditional "Assert required dist artifacts are present" step (`ensure-test-artifacts.mjs --assert-artifacts-present`) runs after the conditional Build step, proving the required dist actually exists on either path before boot-smoke/gate-tests need it.
3. **Verified the 10-path cached dist list is actually everything boot-smoke and `test:gate` read, not just what `REQUIRED_BUILD_PACKAGES` happens to already list.** Grepped every consumer directly:
   - `scripts/boot-smoke.mjs` touches exactly one dist path: `packages/cli/dist/bin.js` (via `packages/cli/bin.mjs`). Already cached.
   - `scripts/check-verifier-confinement.mjs` (part of Gate's verifier-confinement step) imports `packages/engine/dist/index.js`. Already cached.
   - This looked incomplete at first: `packages/dashboard/src/{native-structure-preview,droid-cli-probe,roadmap-routes,report-roadmap-source}.ts` statically `import` from `@fusion-plugin-examples/roadmap` and `@fusion-plugin-examples/droid-runtime`, and `fn serve` (what boot-smoke drives) loads `@fusion/dashboard` (`packages/cli/src/commands/serve.ts` line 31) — neither of those two plugin packages is one of the 10 cached paths.
   - Resolved by reading `packages/cli/tsup.config.ts`'s `cliBuildConfig` (the config that produces `dist/bin.js`/`dist/extension.js`, lines ~385-424): it sets `esbuildOptions(options) { options.conditions = [...(options.conditions || []), "source"]; }` together with `noExternal: [/^@fusion\//, /^@fusion-plugin-examples\//]`. That forces **every** `@fusion/*` and `@fusion-plugin-examples/*` package — dashboard, roadmap, droid-runtime, hermes-runtime, openclaw-runtime, etc. — to be compiled directly from its raw TypeScript source straight into `packages/cli/dist/bin.js` at CLI build time. None of that code is ever read from those packages' own separately built `dist/` folders at runtime. (The one place `@fusion/engine` stays external — `bundlePluginEntry`, tsup.config.ts line ~211 — builds the *separate*, dynamically-loaded plugin-registry bundles; boot-smoke and `test:gate` don't exercise that path.)
   - Conclusion: the existing 10-path `REQUIRED_BUILD_PACKAGES` cache list is confirmed sufficient for both boot-smoke and `test:gate` as they exist today. No paths added to either the save or restore list.

## Known residual gap

Gate's `pnpm build` fallback (the genuine-miss path) has no `NODE_OPTIONS` cap and no standalone desktop pre-build step — the desktop-OOM fix above is scoped to the Build job only, per explicit review guidance. In practice this path should be exceedingly rare now: the cache key is commit-exact and Gate always runs after Build in the same workflow run, so a miss means Build's own save step didn't complete (a prior failure, not routine operation). Gate also runs on the larger `ccc-fusion-bwrap` runner (4 GiB vs. Build's 2.5 GiB), which gives more headroom than the container where the OOM was actually observed. Not fixed here because it's out of the reviewed scope; flagged as a known gap rather than silently left unrecorded.

## Deviation from the initial plan text

The initial plan text listed `packages/i18n/dist` as a path to add to the cache list. `@fusion/i18n` has no `"build"` script and its `exports` map resolves directly to `./src/*.ts` (a source-only workspace package) — `pnpm build` never produces `packages/i18n/dist`. Verified by reading `packages/i18n/package.json`. Omitted from both Build's save list and Gate's restore list; including a path that's never created is inert (`actions/cache` just skips a missing path) but doesn't match what's actually on disk, so it's left out.

## Expected effect (not yet measured live)

Gate no longer pays its own ~5 min redundant build on a cache hit; the critical path becomes roughly Build (~8 min, now including the standalone desktop step) → Gate (restore + gate tests, ~3 min), serialized by the new `needs: build` edge. `needs: build` means Gate only enters the shared two-slot cross-repo admission queue *after* Build releases its own slot, so worst-case wall clock under heavy cross-repo contention is unchanged (~15 min, same as the measured baseline) — Gate still waits its turn, just later. The win shows up in the common case: total wall clock drops toward ~11 min, and total slot-minutes across the two jobs fall by Gate's old ~5 min redundant build (~27.5 → ~22.5). A live PR run against this branch is the actual before/after measurement; this doc records the design and the pre-change baseline only. The measured live numbers belong in the PR description once this branch's own CI run reports, and should be pasted back into this doc as a follow-up edit at that point.
