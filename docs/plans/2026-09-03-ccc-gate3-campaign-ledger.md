## Open work

### L1a — CCC acceptance gate has never been green in CI `IN PROGRESS`

The flagship 39-check whole-product proof (`.github/workflows/ccc-prd-product-gate.yml`) has failed all 4 runs since it was created 2026-08-03. It passes only on Ryan's Mac. The project's most important gate has zero CI evidence.

**Root cause (established 2026-09-03, verified by local reproduction):** three workflows install go-task via `npm install -g --prefix "$RUNNER_TEMP/go-task" @go-task/cli@3.52.0` and put `<prefix>/bin` on PATH. That directory's `task` is a **symlink to `run-task.js`**, a Node ESM launcher. The real platform binary lives at `<prefix>/lib/node_modules/@go-task/cli/bin/task`.

`task` is the declared semantic-proof *verifier* executable (per `docs/ccc-prd-intake-contract.md`, verification must sit behind a `task verify:<slug>` target), so `packages/core/src/ccc-prd/semantic-proof-custody.ts` (`inspectSealedExecutableVersion`, ~line 357) seals the resolved executable and execs it for `--version`. It resolves the symlink to `run-task.js`, seals that, execs it, and fails — a `.js` file is not an executable image. **The gate is correct; the CI toolchain shape is wrong.**

Locally confirmed: real binary and shim both print `3.52.0`. Ryan's local `task` is a real Mach-O binary, which is exactly why this passes locally.

**Fix:** point CI's PATH at the real binary directory. Workflow-only. Affects `ccc-prd-product-gate.yml:111-113`, `pr-checks.yml:288-290`, `full-suite.yml:381-383`.

**Independently confirmed** by pulling the published `@go-task/cli@3.52.0` tarball: its `package.json` declares `bin: {"task": "run-task.js"}`, and its `lib.js` sets `binDir = path.join(__dirname, "bin")` where `__dirname` is the package directory — so the postinstall drops the real per-platform binary at `<prefix>/lib/node_modules/@go-task/cli/bin/task`, exactly matching the `lib/node_modules` segment in the failing CI log.

**Status:** PR **#59**, branch `agent/ci-gotask-real-binary`, commit `b62eb9c11`. Diff is 4 files, +65/−6 — three identical 2-line workflow swaps plus 3 new guard tests in `packages/cli/src/__tests__/ci-workflow.test.ts`. RED captured against unmodified workflows; `test:ci-shape` now 92/92; lint clean. Diff reviewed directly by the orchestrator: no custody code touched.

Acceptance workflow dispatched on the branch as run **33809518230** — deliberately *before* merge, because a merged fix is not proof.

For the first time since the workflow was created on 2026-08-03, the gate got past toolchain custody and ran a real campaign in CI. It now dies on a **10-minute poll budget** (`FUSION_PRODUCT_TIMEOUT_MS: "600000"`, overriding the script's 120 s default at `scripts/ccc-prd-product-acceptance.mjs:66`; the job's own backstop is `timeout-minutes: 45`, so the job did not run out of time — the script's internal poll did).

**Open question, not yet answered:** is 600 s simply too small for this runner, or is something genuinely stuck? Evidence for "too small": the acceptance gate has *never* run this far, so its CI poll budget has never been calibrated; and PR #58 capped postgres service containers at 1 GiB / 1 CPU, which would slow it further. Evidence for "genuinely stuck": `latest=[]` means nothing had progressed, and the serve log shows only self-healing maintenance and stuck-detector polling — a live but idle server. A post-dispatch cutpoint is a *deliberate* fault-injection point in this script, so reaching one is expected; the question is whether recovery from it then stalled.

**ANSWERED — it is a genuine stall, not a small budget. High confidence. Do not raise the timeout.**

The poll at `scripts/ccc-prd-product-acceptance.mjs:5236` calls `readOwnedProofCutpointMarkers` (`:3309`), which `readdir`s the tmp root for a `ccc-semantic-proof-execution-*` directory. That directory exists only once the engine has actually spawned the sandboxed semantic-v2 verifier subprocess. `latest=[]` with empty `error=` means the readdir succeeded on all ~1200 attempts and found **zero** — total absence of dispatch, not a wrong shape and not flaky I/O.

Four independent lines of evidence, any one of which would be suggestive; together they are decisive:

1. **Checks #1–#20 finished in ~72 seconds**, including a complete provider-cutpoint crash/restart/recover/abandon sequence. Then check #21 (`proof-dispatch-restart-manual-required`) alone consumed the remaining 600 s — 89% of the step's wall time — with no progress.
2. **Locally the entire 39-check suite passes in 5 min 02 s** (evidence doc `:181`, pueue 1550). In CI this *one* check burned twice that and never resolved. A slow runner scales everything proportionally; it does not take one check from milliseconds to never.
3. **The budget was already raised 5× before today** (120 s → 600 s), documented in the workflow's own header at `ccc-prd-product-gate.yml:9-24`. It produced *no* behavioral change — same empty result, five times longer. If progress were being made, more time would show something different downstream. Across four runs now, it never has.
4. **PR #58's postgres cap is irrelevant here** — this script drives the CLI's bundled embedded PostgreSQL and strips `DATABASE_URL`, per the workflow's own comment. It never touches the capped service container.

**Stalled component:** on the self-hosted Linux ARM64 `ccc-fusion-bwrap` runner, the engine's proof-execution dispatcher never spawns the bubblewrap-sandboxed verifier after the proof-cutpoint execution is approved. On macOS it does.

**This bug has always been there.** It was invisible only because the gate never got past the toolchain check to reach it. Fixing L1a did not create this — it exposed it.
