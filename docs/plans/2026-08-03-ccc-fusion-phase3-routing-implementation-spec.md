## 1. Scope and non-goals

### In scope

1. **Route profiles** — a reference mapping from fusion task archetype to OmniRoute combo/model identifier (§2), plus the ccc-fusion-side registration surface that makes those identifiers resolvable.
2. **Quota-awareness** — a read path against `quota_snapshots` (directly, or via the fixed `/api/usage/quota` once it lands — see §3, §6) with an explicit staleness guard and a documented degraded state.
3. **Backoff policy** — concrete retry/backoff parameters for the `agy` (Gemini CLI bridge) lane, reconciled against ccc-fusion's *existing* generic retry infrastructure (§4, §6).
4. **Receipts** — wiring `x-omniroute-response-cost` (and the other `x-omniroute-*` headers) into ccc-fusion's existing `CccProviderAttemptCost`/`CccProviderAttemptEffectiveRoute` contract, honoring frozen decision E3 (§5).

### Explicitly out of scope (non-goals)

- **Health-aware balancing is UNAUTHORIZED.** The report proves no trustworthy health observable exists (`get_provider_metrics` reports `requestCount:0` under live traffic; combo metrics conflate cache hits with provider health — report §5, §11). No code in this Phase may branch routing decisions on OmniRoute-reported health, success rate, or latency.
- **A dynamic dispatch engine is UNAUTHORIZED (settled OQ-1).** ccc-fusion does not re-route at runtime — that is the point of frozen E1/E2 (a task's route is declared and locked, not chosen live by product code). §2's mapping table informs the operator's upstream route declarations; it is reference material, never a runtime selector. Product-side work is limited to route-policy metadata that lets admission *refuse* a mismatched declaration — see §2.4.
- **Latency-aware balancing on combo metrics** — same cache-contamination reason (§5). Client-side, cache-busted latency measurement (report §6) is a *measurement* technique, not something to wire into live routing decisions in this phase.
- **Quota-aware balancing on `/api/usage/quota`** — the endpoint is a hardcoded-default bug (§4.3 of the report); it must never be read as a routing input until T-1–T-4 land.
- **Burn-in or use of `top-tier-heavy`, `top-tier-standard`, `hindsight-reflect-deep`** — never measured end-to-end (report §2.4). No route profile in §2 references them, and none should be added without a fresh measurement pass under the operator's spend policy.
- **`pca-receipt-ensemble` and `minor-task-monkey` as-is** — 46.7% correctness and a phantom priority-1 model respectively (report §12.2). Neither gets a route profile entry.
- **Modeling or claiming OmniRoute fallback latency.** Zero fallbacks were observed in 302 requests (report §6.3, gap #2). Nothing in this spec assumes fallback timing.
- **Mutating OmniRoute config, DB, or combo definitions.** Every mechanism below that requires an OmniRoute-side change is called out as LIVE-INFRA in §6 and is not implementer-autonomous.

### 2.4 What "route profile" means here (settled — OQ-1)

I did not find, in the `63f8bbb94` tree, any existing runtime component that dynamically selects a provider/model per task archetype. `packages/core/src/ccc-prd/importer.ts:392,401-414,579,603-653` shows that a campaign task's route (`providerId`, `modelId`, `transport`, …) is read **verbatim** from the imported PRD/campaign bundle's `executionPolicy.routes[]` and threaded straight into task metadata (`cccExecutionProviderId`, `cccExecutionModelId`) — it is authored upstream (by whoever writes the PRD / generates the campaign), not computed by ccc-fusion at dispatch time. `packages/core/src/ccc-campaign/canonical.ts:180-260` validates the shape of an already-authored route; it does not choose one.

**Settled: §2.1's table is a reference table plus a declared route policy — never a runtime dispatch engine.** The product does not re-route at runtime; that is the point of frozen E1/E2 (a route is declared once, locked, and any drift from the declaration is refused, not silently corrected by picking a better one). §2.1 informs the *operator's* upstream route declarations when authoring a PRD's `executionPolicy.routes[]`. It is not proposing, and this Phase must not build, an "auto-pick a combo for this task" engine.

Product-side work is limited to **route-policy metadata that lets admission refuse a mismatched declaration** — the same shape as the incoming `verbatimCapable` flag (Phase 1, `agent/phase1-chunked-understanding` @ `d27fbb7ab`, not yet in `main`): a declared per-model or per-combo assertion, checked fail-closed at admission time, never inferred or auto-corrected. Concretely:

- Registering OmniRoute's combo/model identifiers as resolvable `CustomProvider.models[]` entries (§6.1) is implementer-autonomous ccc-fusion work.
- A route-policy admission check that refuses a declared route naming a combo/model this table doesn't recognize, or naming one of the never-recommended combos (`pca-receipt-ensemble`, `minor-task-monkey` — §2.1), is implementer-autonomous ccc-fusion work, following the same `verbatimCapable`-gate *pattern* (fail-closed at admission, never inferred) that Phase 1's D2 design lands.
- The D3 verbatim-capability admission rule for combo declarations (§5.4) is the concrete instance of this pattern for Phase 3.

That citation is **unverifiable at `63f8bbb94`** — `verbatimCapable` does not exist on `main` at all (`workflow-steps.ts:195` is still `{ id, name, maxTokens?, contextWindow? }`) — and it independently conflicts with the accepted Phase 1/D2 design's own citation for the *same* claimed hook: D2 §8 places enforcement at `native-authoring-adapter.ts:78-95` (invoked at `:259`), scoped to `mode: "understanding"` authoring calls, not `:128`. This relationship, not either gate's line-number citation, is the part of X-F2 that is settled here.

## 3. Quota-awareness design

### 3.1 Never trust the endpoint

`/api/usage/quota` returns a constant `{quotaTotal: null, percentRemaining: 100}` shape for all 13 providers regardless of real usage (report §4.1–§4.3). **No code written under this spec may read `percentRemaining` from that endpoint as a signal.** This holds even after the endpoint fix (T-1) lands, unless the fix is itself re-verified live — see §6 for why that fix is LIVE-INFRA.

### 3.2 `quota_snapshots` schema (pinned from a read-only copy this session)

DB copied to `/tmp/omniroute-storage-ro-copy.sqlite`, opened `file:...?mode=ro`. Never touched the live file at `~/.omniroute-devstack/data/storage.sqlite`.

```sql
CREATE TABLE quota_snapshots (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    provider TEXT NOT NULL,
    connection_id TEXT NOT NULL,
    window_key TEXT NOT NULL,
    remaining_percentage REAL,
    is_exhausted INTEGER DEFAULT 0,
    next_reset_at TEXT,
    window_duration_ms INTEGER,
    raw_data TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_quota_snapshots_provider_time ON quota_snapshots(provider, created_at);
CREATE INDEX idx_quota_snapshots_connection_time ON quota_snapshots(connection_id, created_at);
CREATE INDEX idx_quota_snapshots_created_at ON quota_snapshots(created_at);
```

- **Row count:** 97,471 (report measured 97,221 five hours earlier — consistent with a live collector still running).
- **Span:** `2026-05-27T16:57:11.311Z` → `2026-08-03T21:18:45.635Z`.
- **Providers present:** `antigravity`, `claude`, `codex`, `glm`, `minimax` — **only 5 of the 13 connections** the report enumerates have windowed quota rows at all (no `gemini`, `openrouter`, direct-local, etc.). Any provider absent from this set must default to `unknown`, never to a fabricated 100%.
- **`window_key` is not standardized across providers.** `claude` uses `"session (5h)"` / `"weekly (7d)"`; `codex` uses `"session"`, `"weekly"`, and a third one-off key `"gpt_5_3_codex_spark_session"`. A quota reader must key on the literal `(provider, connection_id, window_key)` tuple — never assume a shared window taxonomy across providers.

### 3.3 Staleness guard

Freshness varies a lot per provider/window and is not on a fixed cadence. Sampled this session (last 15 `claude` / `session (5h)` snapshots): gaps between consecutive rows ranged from ~5 to ~36 minutes — irregular, not a fixed collector tick. Separately, `codex` / `weekly` had not been written since `2026-07-12T18:21:37.886Z` — **22 days stale** at probe time. This is not a hypothetical edge case; it is the live state of one of five tracked providers right now.

**Design:**

- **Default staleness threshold: 30 minutes — kept, settled OQ-7.** This is a conservative default chosen to cover the observed irregular collector cadence (roughly 2× the typical observed gap). The orchestrator's ruling keeps this default rather than blocking on a documented collector interval, but requires the standalone advisory tool (§3.4) to **measure the observed per-provider-per-window snapshot cadence from the data itself** on every run, and to surface (not silently apply) any window whose measured cadence makes the 30-minute default meaningless — e.g. `codex`/`weekly`, last written `2026-07-12` (22 days stale at this session's probe), must report `"no usable signal — conservative behavior, surfaced not silent"` rather than either a false-fresh or a false-stale verdict. The default self-corrects by measurement plus surfacing, never silently.
- **Degraded behavior on a stale or missing snapshot: treat the window as `unknown`, never as `100%` or as "healthy."** This mirrors the report's core fix requirement (§4.4): *"an honest `null` is legal per E3; a fabricated 100 is not."* The same discipline applies here even though this is a quota read, not a cost receipt — silently treating stale-or-absent quota as full headroom is the exact bug being fixed.
- **Surface, don't swallow, degradation.** When a quota reader returns `unknown` because of staleness or absence, that must be observable (logged with `provider`, `connection_id`, `window_key`, computed age) — not silently absorbed into a routing decision that looks identical to "quota confirmed healthy."
- **Multi-window awareness.** A provider like `claude` has two independently-binding windows; a caller must not collapse them to a single scalar (report §4.4 requirement 3). If either window is `is_exhausted` or below a caller-supplied floor, treat the provider as drained regardless of the other window's value.

### 3.4 Read path (settled — OQ-2)

**Settled: product (engine/runtime) code never reads OmniRoute's private DB.** ccc-fusion's shipped engine and library surface (`packages/core`, `packages/engine`) must not open `~/.omniroute-devstack/data/storage.sqlite`, or any OmniRoute-owned storage, at runtime. Coupling the product to a private, undocumented storage layout owned by a separate service is exactly the fragility the report's own findings warn about (broken/contaminated OmniRoute surfaces, §11) — the fix is to keep this out of the product surface entirely, not to harden a runtime dependency on it.

**Quota-awareness ships as a standalone pre-flight advisory tool, not engine runtime.** Concretely:

- Lives in `scripts/` (this repo's existing home for standalone operational tooling — e.g. `scripts/ccc-prd-product-acceptance.mjs`; `scripts/__tests__/` already holds 57 `*.test.mjs` files at this pin, so this placement is idiomatic), not in `packages/core` or `packages/engine`.
- Opens a **read-only copy** or a `mode=ro` connection to `quota_snapshots` (exactly as this session did — copy to `/tmp`, or `file:...?mode=ro`), never the live file directly, never a write handle.
- Applies the staleness guard (§3.3) and the OQ-7 cadence-measurement/surfacing requirement.
- Emits a human/orchestrator-readable snapshot report, consulted **before** launching a run — a pre-flight check, not a runtime dependency any task execution path calls into.

**Rev 3 addition (R-F9) — the read mechanism itself is unspecified and must be decided before this tool can be written.** No SQLite driver is declared anywhere in this repo: `grep -irn "sqlite\|better-sqlite3\|node:sqlite"` across the root `package.json` and every `packages/*/package.json` returns zero hits, and there is no `engines.node` floor or `.nvmrc`, so `node:sqlite`'s availability (Node ≥22.5 experimental, ≥24 stable) cannot be assumed. Three options, none chosen here — this is a small decision but it is the first thing an implementer hits: (a) `node:sqlite`, gated on declaring and verifying a minimum Node version; (b) add `better-sqlite3` (or equivalent) as a new dev dependency scoped to `scripts/`; (c) shell out to the `sqlite3` CLI binary with a documented availability check and a clear failure message if it's missing. §6's advisory-tool row now names this as an explicit sub-decision.

**The broken `/api/usage/quota` endpoint fix (T-1) remains LIVE-INFRA, deferred** (§6, §7) — it lives in OmniRoute's own source tree, not this repo. Product consumption of a *fixed* endpoint (replacing the standalone advisory tool's direct-copy read with an HTTP call) is explicitly **future work, out of scope for Phase 3.**

## 4. Backoff policy

### 4.1 Scope: this is the `agy` (Gemini CLI bridge) lane only

The report's backoff data (§8.6) comes entirely from characterizing `agy -p '<prompt>'` — sequential ≤6.8 req/min for 30 calls, concurrency up to 8. **It says nothing about OmniRoute HTTP combo/direct-model calls.** Zero fallbacks were exercised in 302 gateway requests (report §6.3), so there is no measured retry/backoff behavior for OmniRoute-routed calls at all. Do not invent OmniRoute-side retry parameters under this spec; only the `agy` lane gets concrete numbers below.

**Rev 3 flag (R-F10) — no `agy` CLI dispatch call site exists in this repo yet, and this is a prerequisite, not a detail.** Every verified `withRateLimitRetry` call site (fourteen, listed in §4.2) wraps an in-process pi/agent session — `merger.ts`, `executor.ts`, `agent-heartbeat.ts`, `merger-ai.ts`, `pr-response-run-ops.ts`. None is an `agy` CLI invocation, and no such invocation surfaced anywhere in this repo at `63f8bbb94`. **Before assuming `withRateLimitRetry` is the right home for any of §4's fixes, the implementer must locate — or explicitly commission — the actual `agy` call path.** If `agy` turns out to be invoked only by operator tooling outside the engine (a plausible reading, given it is CLI-bridge tooling, not a provider registered in pi-ai's model registry), the entire §4 workstream may belong in `scripts/` alongside the quota advisory tool (§3.4) rather than in `packages/engine`. This spec does not resolve that placement question; it flags it as blocking before implementation starts.

### 4.2 A close match already exists in the repo — reconcile, don't reinvent

`packages/engine/src/rate-limit-retry.ts:93-167` (`withRateLimitRetry`) already implements: `delay = min(baseDelayMs × 2^attempt, maxDelayMs)` with jitter, defaulting to **`maxRetries: 3`, `baseDelayMs: 30_000`, `maxDelayMs: 120_000`** (`RateLimitRetryOptions`, `:50-67`). That is the 30s → 60s → 120s (cap), 3-retries-after-initial-attempt ladder the report derives independently in §8.6 rule 4 — the existing generic infrastructure's defaults already match the measured/extrapolated policy. This is a strong signal that the *mechanism* to reuse is `withRateLimitRetry`, not a new backoff implementation — **once the R-F10 call-site question above is resolved.**

**Settled (OQ-3), corrected in Rev 3 (R-F3, R-F4, R-F8, R-F11) — fixed inside `withRateLimitRetry` and `usage-limit-detector.ts`, both in `packages/engine`, no new module:**

### 5.2 Mapping `x-omniroute-*` headers into the existing contract

| Observed response state (report §6, §10) | `CccProviderAttemptCost` | `receiptSource` |
|---|---|---|
| `x-omniroute-response-cost` present, numeric, non-zero, and response body carries token usage | `{ amountUsd: <parsed>, source: "omniroute:x-omniroute-response-cost" }` | see §5.3 — enum gap |

This table is the direct implementation of the report's own instruction: *"a real zero like antigravity's 0.0000000000 is a receipt; absence of a header → unknown, never a guess"* — and it is enforced structurally, not just by convention, because `assertNoCostWithoutReceipt` throws if the code tries to claim a nonzero-or-zero `amountUsd` without both a non-null `usage` and a `receiptSource !== "none"`.

Only the per-response `x-omniroute-response-cost` header is a receipt source under this spec.

### 5.2a Where response headers actually reach ccc-fusion code — R-F1, BLOCKER, resolved by gating

**This is the one Rev-3 finding that changes this workstream's classification, and it is resolved by demotion, not by a fix that can ship as "settled."**

§5.2's mapping table was, in Rev 2, classified "Implementer-autonomous — settled." That was wrong, and the spec itself had already half-admitted it: §6's receipts row said the header-parsing call site was "not yet identified." Rev 3 verified exactly how bad that gap is.

Every field is read from pi-ai's `result` object (`:849-850`). **No HTTP response headers are in scope at this call site.** ccc-fusion reaches OmniRoute through the generic custom-provider / pi-ai streaming path (§2.3/R-F7's correction), and pi-ai's `result` surface exposes provider, model, and token usage — it does not expose raw response headers. Repo-wide grep confirms there is no seam anywhere that currently sees `x-omniroute-response-cost` (zero hits for `x-omniroute` outside this spec and the report, per §7's preamble).

**Failure scenario if this had shipped as "settled":** an implementer extends the `receiptSource` enum (§5.3), writes the header-mapping function (§5.2), and then has **nowhere to call it from** — reaching `x-omniroute-response-cost` requires either a change inside pi-ai (third-party, not this repo) or a new transport-level interception layer around the custom-provider HTTP path that intercepts and threads response headers into whatever eventually calls `reconcileCccProviderAttempt`. **Resolved: this workstream is demoted to a two-stage, gated item.**

The explicit possible outcomes of this investigation: (a) pi-ai already exposes raw headers somewhere not yet found by this spec — re-scope Stage 2 around that seam; (b) pi-ai does not expose them and a targeted upstream pi-ai change is required — this is third-party work and needs its own scoping/timeline, likely LIVE-INFRA-adjacent; (c) a wrapper/interception layer around the custom-provider transport (independent of pi-ai) can observe headers before they're discarded — scope that layer explicitly if so.
2. **Stage 2 (gated on Stage 1's outcome) — the enum extension (§5.3) and the header-mapping function (§5.2's table).** This is the only part of the original "settled" classification that survives, and only once Stage 1 names a real call site.

**T-13 is unwritable until Stage 1 resolves** (§7). This is the spec's one honest BLOCKER: not because the mapping logic is wrong (§5.2's table, §5.3's enum choice, and E3's semantics are all independently sound — Rev 3 found no defect in any of them), but because there is currently no code path in this repo that could call the mapping function with real data.

### 5.3 `receiptSource` gap — settled (OQ-4): extend the enum

`CccProviderAttemptReceiptSource` (`types.ts:188`) is a **closed 3-value union** at `63f8bbb94`: `"stream-usage" | "provider-api" | "none"`. `x-omniroute-response-cost` is neither pi-ai's own stream-token accounting (`"stream-usage"`) nor a direct provider billing API response (`"provider-api"`, strictly read) — it's a gateway-computed, per-response header.

**Settled: extend the enum with a new value, `"gateway-header"`, for `x-omniroute-response-cost`-derived receipts.** Reusing `"provider-api"` would misstate provenance, and E3 is a provenance-honesty rule (§5.1) — collapsing "the gateway computed this from a header" into "the provider's API returned this" is exactly the kind of imprecision E3 exists to prevent, even though it costs a type-surface change.

*Verification note on the cited precedent:* the orchestrator's ruling cites an "already-adopted fourth value `\"cli-transcript\"` for transcript-derived receipts" as precedent. A repo-wide search of the pinned `63f8bbb94` tree (`grep -rn "cli-transcript"`) found no such value — `CccProviderAttemptReceiptSource` is still exactly the 3-value union quoted above at this commit. The precedent may exist on a branch or in work not yet merged to `main`, or may not exist yet at all; either way it doesn't change the ruling, which stands on its own provenance-honesty rationale. Flagged here rather than silently asserted as verified, per this spec's citation discipline.

**Mechanical consequence for the implementer:** adding `"gateway-header"` is not a pure additive change — `packages/core/src/ccc-campaign/provider-attempt.ts:233-241` (`requireReceiptSource`) and `:352-363` (`parseEffectiveRouteReceipt`) validate this union strictly, and `provider-attempt.ts:519-527,555-573` (`exactMetadataKeys`/`parseMetadata`) enforce **exact** key sets per schema version across every existing campaign call site. The implementer must audit **every exhaustive switch statement and every `validateExactKeys`/`exactMetadataKeys`-style closed-set check** that touches `CccProviderAttemptReceiptSource` or `CccProviderAttemptEffectiveRoute`/`...Input` — not just the two functions named above.

**Rev 3 addition (R-F2) — a second, independent closed-set validator lives in a different package and was missed in Rev 2.** `packages/engine/src/cli-agent/ccc-native-cli-binding.ts:714-715` hard-codes the identical triple-literal check:


and the same file duplicates the effective-route key set at `:190` (`EFFECTIVE_ROUTE_KEYS`), independently of `provider-attempt.ts:269` — a parallel validator, not a re-export. **Without updating this file, a `receiptSource: "gateway-header"` attempt that passes every `packages/core` check would still be refused inside `packages/engine`'s CLI-transport binding**, with an error message that still enumerates the old three values. §6 now carries this as its own row.

Rev 2's "gate-fixture" sentence was also wrong and is replaced here: the acceptance gate (`scripts/ccc-prd-product-acceptance.mjs`) does **not** enumerate this union at all — `grep -n "receiptSource|effectiveRoute|stream-usage|provider-api"` against it returns zero hits — so there is no gate-fixture surface to audit. ### 5.4 Combo routing vs. `route-drift` refusal — settled (OQ-5)

`assertCccProviderAttemptEffectiveRoute` (`provider-attempt.ts:299-332`) throws `route-drift` — *"campaign fallback is not an admitted behavior"* — the instant `effectiveModel`/`effectiveProvider` differ from the requested `providerId`/`modelId`. A combo is, by construction, allowed to serve via any of its declared chain members (report §9: identity fidelity was checked against *combo membership*, not exact-model-match). Naively requiring textual equality between a combo name and the underlying served model would trip `route-drift` on every single combo call, which is wrong — but naively loosening the check for every route would silently readmit real campaign fallback, which E3 exists to forbid.

**Settled: requested-identity granularity is the operator's declaration.** If the declared route names a combo, the combo *is* the requested identity, at whatever granularity the operator declared it. This is not a weakening of E2/E3 — it is E2's existing requested-vs-effective two-layer shape (declare one identity, verify what actually served against it) applied to a new identity kind that didn't exist when that shape was designed. Two branches, both enforced, neither optional:

**Branch A — declared route names a combo** (e.g. `providerId: "omniroute"`, `modelId: "pre-flight-query-decanter"`):

- The combo **is** the requested identity. `bindingHash` (computed from the declared, locked route — `canonical.ts`'s `createCccCampaignAuthorityBinding`, already fixed at reservation time regardless of this ruling) carries the combo identity, unchanged.
- `effectiveProvider`/`effectiveModel` in `CccProviderAttemptEffectiveRoute` are recorded from the **trusted `x-omniroute-provider`/`x-omniroute-model` headers** — i.e. the actual chain member that served (e.g. `antigravity` / `gemini-3.1-flash-lite`), not forced equal to the combo name.
- **Refusal rule (mechanical change to `assertCccProviderAttemptEffectiveRoute`, `provider-attempt.ts:299-332`):** for a combo-declared requested identity, the drift check is *membership*, not *equality* — refuse only if `effectiveModel`/`effectiveProvider` is **not** a declared chain member of the requested combo. Serving via any declared member is not drift; serving via anything else still is.
- **Rev 3 correction (R-F5) — the data path for "declared chain member of the requested combo" was unspecified, and the obvious reading breaks the function's own contract.** `assertCccProviderAttemptEffectiveRoute`'s docstring (`:291-298`) states it is **"Pure and side-effect free so it can be exercised without a database,"** and its sole call site (`provider-attempt.ts:1243-1246`, inside `reconcileCccProviderAttempt`) builds `requestedIdentity` from two plain strings (`attempt.scope.binding.providerId`, `attempt.scope.binding.modelId`) **inside a write transaction** (`withinWriteTransaction`, `:1240`). Combo chain membership is not derivable from those two strings alone — it lives behind a live `GET /v1/combos` call (§2.3). Fetching it inside this function would mean either performing a network read inside a pure, DB-transaction-scoped `packages/core` function (breaking the documented purity contract, and adding exactly the OmniRoute runtime coupling OQ-2 forbade for `quota_snapshots` — §3.4), or silently changing the function's signature without saying so. **Settled here instead: the declared combo's chain is resolved once, at admission/lock time** (the same admission step that runs the D3 verbatim-capability gate below — same input, same timing), **and carried forward as inert, already-resolved data** — either on the locked binding itself or threaded through `CccProviderAttemptReconciliationInput` to the reconciliation call — so `assertCccProviderAttemptEffectiveRoute` continues to do zero I/O and stays exactly as pure as its docstring already claims. This also keeps E1 honest: the live `/v1/combos` resolver is authority *at admission*, not re-consulted at settlement time. §6 carries this threading surface as its own row.
- **Proposed RED tests (new — T-15, T-16 in §7):** (T-15) a combo-declared attempt, given a resolved chain-membership list as an input, whose `x-omniroute-model` matches a member of that list settles without a `route-drift` refusal; (T-16) the same, given `x-omniroute-model` that is *not* in the resolved list, is refused as `route-drift`. Both tests construct the resolved chain as plain input data — neither performs a live `/v1/combos` call, consistent with the corrected pure-function design above.

**Branch B — declared route names a specific model** (not a combo): **strict identity semantics are unchanged.** `assertCccProviderAttemptEffectiveRoute`'s existing exact-equality check (`provider-attempt.ts:320-329`) continues to apply exactly as today. If a model-declared route somehow gets served through a combo mechanism that swaps in a different model underneath it, that **is** drift and is refused — full stop, no membership exception. **Proposed RED test (new — T-17 in §7):** a regression test confirming a model-declared route's effective identity still fails strict equality (refuses) even after Branch A's membership logic exists, so an implementer cannot accidentally loosen the check for every route instead of only combo-declared ones.

**D3 extension — verbatim-capability admission gate for quote-bearing combos.** A combo declared for a quote-bearing/verbatim-extraction task archetype (§2.1's "bulk verbatim extraction" row) is admissible **only if every member of its declared chain** carries `verbatimCapable: true` in its registered `CustomProvider.models[]` metadata (the incoming Phase 1 flag — §2.4, X-F2). Refusal is fail-closed **at admission time** (before any attempt is ever reserved). This is not optional given Branch A: once *any* declared chain member is a legitimate non-drift outcome, a combo with even one non-verbatim-capable member could silently serve a quote-bearing task through that member and produce paraphrased output with zero identity-check refusal — D3 closes that hole upstream, at declaration time, rather than trying to catch it per-attempt.

**Rev 3 correction (R-F6) — the gate as described in Rev 2 is placed in a layer that cannot reach either of its own inputs. Three distinct problems, all real:**

1. **Layering.** Route admission in `packages/core` is pure over (plan JSON, bundle): `parseRoute` (`canonical.ts:179-220`) and `parseProductRoute` (`canonical.ts:267-360`) validate shape and path containment only, over plain `unknown` input, with no I/O. `CustomProvider.models[]` is read from `<globalDir>/settings.json` by `readCustomProviders` (`packages/engine/src/custom-providers.ts:6-15`) — engine-side, filesystem I/O. `packages/core` cannot reach it, and Rev 2's "`canonical.ts`-adjacent" hedge never actually resolved this. **Corrected: the D3 gate moves to a named engine-side admission step**, not `packages/core`, run **before** route lock.
2. **Chain membership, same gap as R-F5.** The gate also needs the combo's declared chain — the same live `/v1/combos` read R-F5 identified. **Same fix applies:** the chain is resolved once at admission time (this engine-side step is exactly where R-F5's resolution already happens) and handed down as data, not re-fetched.
3. **Chain members are not yet registered models, and nothing commissions that.** §6's registration row commissions "OmniRoute registered as a `CustomProvider`... with combo/model names in `models[]`" — but for "every chain member has `verbatimCapable: true`" to be checkable, each individual chain member (e.g. `gemini/gemini-3.1-flash-lite`, `antigravity/gemini-3.1-flash-lite`, `omlx-local/gpt-oss-20b-OptiQ-4bit` — §2.3) must *itself* be a `CustomProvider.models[]` entry, and a mapping from an OmniRoute chain-member identifier to a registered model id must exist. **Neither is commissioned anywhere in Rev 2** — T-19 gestured at it parenthetically but no §6 row owned the work. Note the entry shape is `{ id, name, maxTokens?, contextWindow? }` (`workflow-steps.ts:195`) — **there is no per-entry provider field**, so where a chain member's provider prefix (`antigravity`, `gemini`, `glm`, `omlx-local`) is stored is itself undecided; the simplest reading is that the registered `id` string carries the full `provider/model` form already used throughout §2's chain listings (e.g. `id: "antigravity/gemini-3.1-flash-lite"`), but this spec does not mandate that convention — it commissions the registration + mapping work explicitly (§6) and leaves the exact identifier scheme to the implementer rather than inventing one here.

**Also corrected: the `native-authoring-adapter.ts:128` citation as "the exact pattern already landed" is withdrawn** — see §2.4's Rev 3 correction (X-F2) for why that citation is unverifiable at this pin and conflicts with the accepted Phase 1/D2 design's own citation for the same claimed hook.

**Proposed RED tests (new — T-18, T-19 in §7):** (T-18) given a resolved chain and a `readCustomProviders()` snapshot as explicit inputs to the new engine-side admission step, a combo declared against the bulk-verbatim-extraction archetype is refused when any one chain member's registered model entry lacks `verbatimCapable: true`; (T-19) the same, given every chain member's registered entry has it, succeeds. Both are written against the corrected engine-side placement, not the withdrawn `packages/core` placement.

### 5.5 Identity verification (report §12.3 point 2 — "safely usable right now")

Independent of the receipt question: `x-omniroute-model` / `x-omniroute-provider` should be asserted against the requested combo's declared chain (from raw `GET /v1/combos`, §2.3 — never the MCP tool surface, per the OQ-8 rule in §2.3), and an assertion failure should alarm rather than pass silently. This is the one trustworthy runtime signal the report proves (0/302 identity exceptions).

Two distinct mechanisms now exist, related but not the same, both grounded in this identity check:

- **T-6** (§7): a general-purpose identity guard for *any* OmniRoute-routed call, independent of whether it's tracked as a campaign provider attempt — the right place for this is engine-level (`packages/engine/`), and it's the broader net.
- **T-15/T-16** (§5.4, §7): the *specific* membership check inside `assertCccProviderAttemptEffectiveRoute` (`provider-attempt.ts:299-332`) for combo-declared campaign attempts, settled under OQ-5. Both should exist; neither substitutes for the other.

### Merge-order dependency on Phase 1 (X-F3)
