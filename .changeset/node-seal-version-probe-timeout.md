summary: Give semantic-proof executable version probes a cold-start-safe timeout and a diagnosable, bounded failure message.
category: fix
dev: A freshly-sealed executable's first `--version` launch is a genuine cold start every time (fresh ad-hoc code signature, new mkdtemp root, no cache to warm across proof rounds). Semantic-proof preparation is serialized host-wide to exactly one in flight at a time (semanticProofPreparationSemaphore), so the cost here is not contention -- it's amfid validating every file in the executable's linked-dylib closure the first time that exact signed content is ever presented to it, sequentially, at roughly 1-2s per file. The live Gate 3 halt this bound is sized against hit that cold case directly: the unified log shows amfid rejecting node's binary and all 17 of its linked dylibs one at a time (ad-hoc/unknown-certificate-chain, non-fatal but real per-file cost), spanning 18.417s end to end, with zero syspolicyd activity and zero concurrency involved. The previous 10s bound covered neither the original probe nor its one retry. `EXECUTABLE_PROBE_TIMEOUT_MS` is raised to 45s (~2.4x margin over that single directly observed worst case; the existing single retry-on-timeout is unchanged, no new retries added). A warm-cache isolated single probe against the same real dylib closure measures 3.6-4.2s across 10 sequential trials, confirming the 45s bound is sized for genuine first-encounter validation, not routine operation. Probe failures now carry `(timedOut=<bool> exit=<code|null> signal=<sig|null> attempt=<n>/<total> after <ms>ms totalElapsedMs=<ms>ms) <command> stderr: "<excerpt>"`, envelope first and the (potentially long, path-bearing) command line last, since both the campaign custody-refusal path and `toolchainDrift` only ever surface `error.message` and the latter slices it to 240 chars -- leading with the short fixed-shape envelope keeps timedOut/exit/signal/attempt legible even when a sealed-toolchain path alone would otherwise consume nearly the whole budget. The stderr excerpt is taken directly from the raw Buffer/string, bounded to 4KB and included exactly once; the base message no longer reuses execFile's own `.message`, which already embeds the full (unbounded, up to maxBuffer) stderr a second time. The 4KB bound is on real byte length, not `string.length` (UTF-16 code units), and a cut always lands on a UTF-8 code-point boundary with a trailing "...[truncated]" marker, so multi-byte stderr is never silently sheared into an invalid sequence. When the command line and stderr excerpt are both empty, the message ends cleanly at the envelope's closing paren rather than a dangling trailing space. otool/install_name_tool/git shellout timeouts are untouched.
